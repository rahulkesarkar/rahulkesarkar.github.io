FLAGSHIP PROJECT / AI · INFORMATION RETRIEVAL

AI Job-Matching Agent.

An end-to-end application that turns a candidate’s resume into a structured profile, filters a job corpus using explicit eligibility rules, retrieves relevant roles with lexical and semantic search, and explains selected matches with evidence-grounded AI analysis.

01 / THE PROBLEM

Finding relevant work is more than a keyword search.

Job descriptions and resumes express similar capabilities in different language. A simple keyword match can miss semantically related experience, while a similarity score by itself can surface roles that are clearly unsuitable for a candidate’s target role, location, seniority, or experience.

The project explores a more careful pipeline: understand the candidate’s explicit evidence, apply transparent eligibility constraints, retrieve with two complementary approaches, and provide a reasoned explanation for an individual posting.

Scope: This is a research and engineering prototype built on an archived dataset. It is not a live vacancy aggregator, a hiring decision system, or a predictor of interview or offer probability.

02 / OBJECTIVES

What the system is designed to do.

  • Extract selectable text from a PDF resume and form a structured candidate profile.
  • Keep user-selected target roles separate from resume-derived evidence.
  • Apply candidate-aware eligibility filters before ranking.
  • Compare a traditional TF-IDF baseline with semantic vector retrieval.
  • Aggregate chunk-level similarity into job-level recommendations and reduce near-duplicate results.
  • Explain selected jobs using deterministic Python calculations plus a locally hosted LLM.
  • Expose the workflow through a FastAPI backend and Streamlit interface.

From resume upload to ranked results.

04 / DATA ENGINEERING

Prepare the corpus before searching it.

The source is the Role Radar dataset hosted on Hugging Face. It contains 2,500 scraped job records collected on April 30 and May 1, 2026. The corpus is archived and must not be represented as currently open vacancies.

Preprocessing includes location normalization, duplicate-ID removal, description-quality checks, token-length auditing, chunk generation, embedding generation, and FAISS index construction. Raw and generated datasets are excluded from the public repository.

The dataset card advertises Apache-2.0, but redistribution rights for individual third-party job descriptions have not been independently established. The raw job data is therefore not committed.

05 / RETRIEVAL ENGINEERING

Two complementary ways to find relevance.

TF-IDF baseline

Scikit-learn’s TF-IDF vectorizer uses unigrams and bigrams to establish a conventional lexical retrieval baseline. Candidate and job vectors are compared using cosine similarity.

Semantic retrieval

The embedding model is sentence-transformers/all-MiniLM-L6-v2. It produces 384-dimensional embeddings. Job descriptions are split into token-aware chunks (200 tokens with 40-token overlap), normalized, and indexed in FAISS using IndexFlatIP. For normalized vectors, inner-product ranking is equivalent to cosine similarity.

Job-level aggregation

Each candidate chunk searches the indexed job chunks. The maximum chunk-pair similarity is retained per job, avoiding repeated job cards caused by multiple matching chunks.

Recommendation diversification

Near-duplicate postings are grouped using normalized company, title, location, and description similarity. The current description-similarity threshold is 0.995; alternate posting IDs are retained.

06 / CANDIDATE ELIGIBILITY

Filter obvious mismatches before ranking.

Eligibility rules run before both retrieval methods and pass the same eligible job set to TF-IDF and semantic ranking. The current logic considers target roles, an India location preference, experience requirements, seniority, and education evidence, including explicit equivalency conditions.

These are deterministic heuristics, not a complete understanding of every employer’s requirements. An absent skill in a resume is not proof that a candidate lacks that skill. Recruiters and candidates should review the original job description and the evidence behind the result.

07 / LLM-ASSISTED ANALYSIS

Use AI for explanations, not unchecked facts.

Selected-job analysis uses Qwen3 4B through local Ollama by default. Python owns the deterministic calculations: recognized required-skill overlap, coverage, and skill gaps. The LLM provides supporting natural-language explanations.

  • Structured output is validated with Pydantic.
  • Unsupported-claim checks help constrain generated statements.
  • Invalid or unavailable LLM output triggers a deterministic fallback.
  • Coverage is explicit taxonomy overlap — not an overall fit score or hiring probability.

FastAPI owns request validation and orchestration. Streamlit provides PDF upload, target-role selection, candidate evidence, eligible/excluded counts, ranking tabs, and selected-job analysis. Uploaded resume bytes are processed in memory and are not persisted by the current application.

10 / TESTING & REPRODUCIBILITY

Protect the workflow with automated checks.

The repository documents a latest full test run of 92 passed, 5 warnings. Coverage includes resume parsing and profiling, education extraction, eligibility filtering, hardware selection, LLM validation and fallback, and API behavior. The warnings are recorded as non-blocking SWIG/PyMuPDF deprecation warnings.

The data-preparation script defaults to validation-only mode; rebuilding processed data, embeddings, and the FAISS index requires an explicit --run flag. This helps prevent accidental expensive rebuilds.

11 / LIMITATIONS

Known gaps, stated clearly.

  • Archived job data is not a live vacancy feed.
  • OCR for scanned resumes is not implemented.
  • Resume extraction and eligibility rules are heuristic.
  • Authentication and rate limiting are not implemented.
  • Production deployment and load testing have not been completed.
  • Evaluation coverage is limited and does not establish general performance.
  • Third-party job-description redistribution rights have not been independently established.

12 / NEXT STEPS

From local prototype to a safe public demo.

The next engineering milestone is deployment: package the API, model, and indexed corpus in a suitable host; configure a secure public origin; add request throttling and abuse protection; validate upload handling; and test the complete recruiter journey with representative PDFs.

Only after those checks pass will the portfolio embed or link to a live demo. A static page or simulated result is not a substitute for a functioning backend.
